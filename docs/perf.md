# 性能基线

测量程序：`tests/perf_bench.cpp`，目标名 `xyzpdf_perf_bench`。
`tools/build_all_tests.py` **编译**它但**不运行**它（名字里含 `bench` 的目标都被跳过），
因为它输出的是数字而不是通过/失败。

```
python tools/build_all_tests.py                       # 编译
build-local-release\tests\xyzpdf_perf_bench.exe tests/fixtures
```

不写成"断言某个毫秒数"的测试：任何阈值都会在第一次于一台慢机器上变红时被调高，
那样测试就成了传说。这里只记录，回归表现为某一列变了，而不是一个红灯。

## 可复现基线：`tests/fixtures/`

仓库里就有的文件，任何人都能重跑对照。`huge.pdf` 600 页、186 KB，每页一行文字；
`scan.pdf` 3 页、149 KB，每页是 300 dpi 的 A4 位图（解压后 26 MB/页）、**没有任何文字**。

### `huge.pdf` —— 规模

| 测量 | 值 | 备注 |
|---|---|---|
| 打开 | 10.8 – 12.0 ms | 600 页 |
| 读取全部页面尺寸 | 26.9 ms | 44.8 ms / 千页 |
| 渲染 40 页（全文件均匀取样） | 19.4 – 22.5 ms | 约 0.5 ms/页，793×1123 px |
| 读取全部页文字 | 6.8 ms | 0.01 ms/页；共 11892 字符 |
| 全文搜索 | 0.05 ms | 600 命中 |
| 600 页灌进 64 MB 缓存 | 279 – 282 ms | **峰值 61.1 MB / 64 MB，留 18 条** |
| 三次运行的峰值工作集 | 135.9 MB（±0.1%） | 进程整个生命期的峰值 |

**最重要的一行是缓存那行**：M1 的验收标准之一是"内存有上限"。三次运行峰值
**完全相同**（61.1 MB、18 条），说明淘汰是按字节确定性生效的，而不是"这次恰好没涨"。

注意基准里用的是 64 MB，而出厂默认是 256 MB（`RenderCache::DefaultMaximumBytes`）——
故意用小限额，是为了在几十页内就逼出淘汰、从而能观察到上界。

### `scan.pdf` —— 纯图页面

| 测量 | 值 | 备注 |
|---|---|---|
| 打开 | 0.6 ms | 3 页，磁盘上只有 149 KB |
| 渲染 | **30.0 ms/页** | 793×1123 px，源图 2480×3508 |
| 文字层 | **none** | 搜索 0 命中——这是这个文件存在的理由 |
| 3 页灌进 64 MB 缓存 | 88.8 ms | 峰值 10.2 MB，留 3 条（每页约 3.4 MB） |

**这一行才是该盯的数字**：同一台机器、同一个缩放，扫描件的一页比合成文字页贵
**约 60 倍**（30 ms 对 0.5 ms）。30 ms 已经超过 60 Hz 下两帧的时间，所以快速滚动
扫描件时**必然**会先看到占位色、随后页才补上——这是设计上的正确行为（异步渲染 +
占位），但它是被测量确认的，不是被假设的。M1 的"扫描件可正常翻页"以此为据。

它同时也是"每页 10 MB+"那条要求：磁盘上小是因为扫描页大片纯白、Flate 极擅长，
**代价在解压之后**——每页 26 MB 的 RGB 采样。


## 只为看量级：真实文档

这两个文件**不在仓库里**（在 `H:\pdf_test\`），所以下面的数字别人无法复现。
列在这里是为了把合成文件和真实出版物放在同一把尺子上。

| 文档 | 页数 | 大小 | 打开 | 渲染 | 取文字 | 全文件渲染完 |
|---|---|---|---|---|---|---|
| `CH340.PDF`（含照片的数据手册） | 6 | 168 KB | 3.0 ms | 5.2 ms/页 | 1.73 ms/页 | 26 ms |
| `VerilogHDL硬件描述语言.pdf` | 172 | 4.85 MB | 49.8 ms | 4.5 ms/页 | 1.59 ms/页 | 687 ms |
| `scan.pdf`（合成扫描件） | 3 | 149 KB | 0.6 ms | **30.0 ms/页** | 无文字层 | 89 ms |
| `huge.pdf`（合成文字） | 600 | 186 KB | 11.4 ms | 0.5 ms/页 | 0.01 ms/页 | 279 ms |

缓存上界在每一份上都成立，包括 172 页全渲染灌进 64 MB 时（峰值 63.7 MB、留 25 条）。

按真实出版物的 4.5–5.2 ms/页算，一屏（1–2 页）约 9 ms，低于 60 Hz 的 16.7 ms 一帧；
整本 172 页全渲染也才 0.7 秒。扫描件是例外，见上面那一行。

## 没有证明什么

这份记录刻意不说自己证明了它没测的东西：

1. **没有测帧时间。** 上面所有数字是 PDFium 渲染、文字提取和缓存的成本，
   不是"每秒多少帧"。要直接证"滚动不卡"需要测真实窗口下的 paint 与帧间隔。
2. **`offscreen` 平台。** 没有真实合成器，QWidget 的绘制成本不在此列。
   渲染与缓存部分是真实的，屏幕绘制部分不是。
3. **没有 500+ 页的真实文档。** `huge.pdf` 是合成的、每页一行字，它证明的是
   **规模**（600 页的页树、缓存、跳转）而不是真实内容的开销。PLAN §5 要的
   "大文件（500+ 页）"此前**根本不存在**（最大 fixture 只有 40 页），所以
   M1 那句"500 页文档滚动不卡"在此之前无从测量；现在有了文件，内容仍是合成的。
4. **扫描件是合成的。** `scan.pdf` 有真实扫描件的**形状**（300 dpi、纯图、无文字层、
   单页 26 MB 采样），但不是扫描仪的输出：没有 JPEG 噪声、色彩失真或倾斜。
   它能测降采样与内存，测不出真实压缩图的解码开销——那要一份真扫描文档。
5. **单次冷缓存。** 没有测热缓存下的重复访问，也没有测并发。

## 什么时候该更新这里

- 改了渲染、缓存、排版或文字提取的任何一处；
- 换了 Qt / PDFium 版本；
- 拿到了一份真实扫描文档或 500+ 页的真实出版物——那时上面第 3、4 条缺口才算补上。
