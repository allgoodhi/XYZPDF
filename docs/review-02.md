# 第二轮：实际打开 PDF 很卡、页面一直是灰色（2026-09-16）

用户报告：实际打开 PDF 用起来非常卡，页面渲染出来都是灰色的。

下面的数字是在这台机器上实测的（Qt 6.11.2 的 QPdfDocument，595x842pt 的 A4 页，
屏幕 2560x1440）。探针代码在 scratchpad 里，没有进仓库。

```
viewport  dpr   rendered px      MB/page   render ms   256MB 缓存能装几页
   1280        1    1256x 1777       8.5        3         30
   1900     1.25    2345x 3318      29.7        2          8
   2500        1    2476x 3504      33.1        3          7
   2500     1.25    3095x 4380      51.7        4          4
   2500      1.5    3714x 5256      74.5        6          3
```

窗口最大化时视口宽度约 2500 逻辑像素，所以**在这台机器上"适应宽度"的一页就是
33 MB（100% 缩放）到 52 MB（125% 缩放）**。这个数字是后面所有问题的放大器。

---

## 1. 【根因】`PageView::images` 是一个没有上限、永不淘汰的哈希表

`src/view/pageview.h:154`：

```cpp
QHash<int, QImage> images;
```

`setPageImage()`（`pageview.cpp:243`）往里插，而**清空只发生在
`dropPageImages()` 和 `setPageSizes()`** —— 也就是换文档、改缩放、旋转、换屏 DPI。
**单纯滚动的时候，它只增不减。**

于是：滚过 20 页 = 660 MB；滚过 50 页 = 1.6 GB。在 125% 缩放下再翻一半。
这就是"越用越卡"。

更糟的是这份是**第二份拷贝**。`RenderCache` 那个 256 MB 的 LRU 预算做得很仔细，
但它不是画到屏幕上的那一份 —— 画的是 `images` 里的。所以真实内存 ≈
`images`（无上限）+ `RenderCache`（256 MB），而那个认真算过的预算约束不到任何东西。

**改**（二选一，推荐后者）：

- (a) 把 `images` 删掉，让 `paintEvent` 通过一个回调向 `DocumentTab` 要图，
  `RenderCache` 成为唯一一份。最干净，但 paint 路径上要带 token（尺寸、旋转）。
- (b) **推荐**：`requestVisiblePages()` 算出 `wanted` 之后，把 `images` 里不在
  `wanted` 里的页删掉。一个循环的事，内存立刻被限制在"可见页 + 预取"这个集合上，
  而且 `RenderCache` 这才开始干它本来的活 —— 往回滚是缓存命中，不用重渲染。

## 2. 【严重】一次失败的渲染会让那一页永远是灰的

`PageView::setPageImage()`：

```cpp
if (image.isNull() || page < 0 || page >= pageCount())
    return;
```

空图直接丢弃 —— 但 `requested[page]` 里**还记着这一页"已经要过了"**，
而 `requestVisiblePages()` 的去重判断只看 `requested`：

```cpp
if (already != requested.constEnd() && already.value() == pixels)
    continue;
```

所以这一页再也不会被请求第二次，**永远停在灰色占位上**，直到下一次
`dropPageImages()`。

配合第 1 条这就是"渲染出来都是灰色"的完整解释：内存被 `images` 吃光之后，
`QPdfDocument::render` 开始返回空图（一页要连续分配 33–52 MB），每一张空图
都让对应的页**永久**变灰。越滚越多，回不来。

**改**：`setPageImage()` 收到空图时 `requested.remove(page)`，让下一轮重新要。
再补一条 smoke：喂一张空图进去，断言这一页会被重新请求。

## 3. 【结构】只做了"只渲染可见的页"，没做"只渲染可见的区域"

`docs/PLAN.md` §3.3 第 3 条要的是"只渲染看得见的"，现在实现的是**可见的页**，
整页按当前缩放全幅光栅化。`QPdfDocumentRenderOptions::setScaledClipRect` 在
`src/` 下一次都没出现过。

后果就是上面那张表：适应宽度已经 33 MB/页，而缩放上限是 800% ——
`595 × 8 × 1.5 = 7140` 宽，一页 **288 MB**，比整个缓存预算还大。
`RenderCache::evictToFit` 的"受保护条目"分支会把它留下并超预算，
所以放大到高倍数时内存是按单页几百 MB 在走。

**改**（M1 范围内的最小版本）：当一页在当前缩放下大于视口时，只渲染与视口相交
的那块，用 `setScaledClipRect` 指定，`PageView` 按块贴图。至少要有一个绝对上限：
任何一次渲染的像素数不得超过视口面积的某个倍数（比如 4 倍），超过就走裁剪路径。
完整的分块缓存可以留到 M3，但"一页 288 MB"这件事必须现在就堵死。

## 4. 【放大器】预取上下各一整屏，把活跃图像数乘了三倍

`pagesIntersecting(visible, 1.0)`（`pageview.cpp:330`）取的是可见区域上下各扩
一个视口高度。适应宽度时一屏约 1 页，所以活跃集合是 3–5 页 —— 在 33–52 MB/页
的量级上，光预取就是 150–250 MB。

**改**：预取按**字节**算而不是按视口算。比如"在预算内尽量往前后各取"，
预算取 `RenderCache` 上限的一个比例。退一步的话，把 1.0 调成 0.5 也能立刻缓解。

---

## 需要用户确认的一件事

上面的渲染耗时（1–6 ms）是**合成的纯文字 PDF** 测出来的。真实文档里带扫描图、
大量矢量图形的页，单页可能是几百毫秒 —— 那会让第 1、2 条发作得更快，也会让
"卡"里多一份等待。**把实际打开的那个 PDF 的路径给我**，我拿同一个探针跑一遍，
确认渲染耗时这一半是不是也有问题，还是纯粹是内存的问题。
