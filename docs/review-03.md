## 一、框架：三件结构上的事

### 1.1 `Document` 这个抽象目前是名义上的

PLAN §3.2 说它是"为 v2 编辑留的唯一抽象"。实际情况：

- `PageView` 吃的是 `Document *`（`setDocument(backend.get())`）—— 这一半是真的；
- `DocumentTab` 持有的是 `std::unique_ptr<QtPdfBackend>`，不是 `std::unique_ptr<Document>`，
  因为它要 `backend->pdfDocument()` 把 `QPdfDocument *` 交给 `QPdfPageRenderer`；
- `DocumentTab` 还直接对 `*backend` 调 `Print::run` / `ImageExport::run` / `WordExport`。

所以**换一个渲染后端（PLAN M5 的 PDFium 那一步）要动的不是一个 typedef**，
而是 `DocumentTab`、`PageRenderer` 和三条导出路径。

这不是现在要改的事 —— 为一个还没动笔的后端提前抽象是另一种浪费。
写在这里是因为 PLAN 里那句"唯一抽象"读起来像"换后端只动一处"，而它不是，
**这个代价要在决定走 PDFium 那一天之前就知道**，不要在那天才发现。

### 1.2 `DocumentTab` 已经是这个项目里最该拆的一个类

1474 行，它同时是：视图宿主、渲染调度、缓存持有者、搜索会话、选择、OCR 会话、
翻译会话、Word 导出会话、图片导出、打印、七样结构编辑的入口、缩略图面板与书签面板的宿主。
`MainWindow` 2510 行，同样在长。

现在还没塌，因为每一块都写得干净、各自有测试。但**再加一样文档级功能**（注释、表单填写、
或者 PLAN M2 还欠的属性框）就会继续往这一个类里加，而它已经是一屏滚不完的头文件。

可以考虑的一刀（不急，但要有个方向）：把"拿文档去做一件事、会花时间、有进度、可取消"
这一族（搜索 / OCR / 翻译 / Word 导出 / 图片导出 / 打印）抽成一个
`DocumentServices`（或各自一个小 controller），`DocumentTab` 只留"视图 + 文档状态 + 编辑会话"。
取消与生命周期那套（`QSharedPointer<QAtomicInt>` + `~DocumentTab` 里 `waitForFinished`）
已经写对了五遍，抽出去正好让它只写一遍。

### 1.3 编辑与阅读是两条不相通的路 —— 而这条是用户能看见的

`deletePages()` / `rotatePages()` / `movePages()` / `mergeFile()` / `splitInto()` /
`addWatermark()` / `setOutline()` 全部只往 `DocumentEditor` 的操作列表里记一笔，
然后 `Q_EMIT editStateChanged()` 让标题加个星号。**`PageView` 一个像素都不变。**

也就是说：删掉第 5 页，屏幕上第 5 页还在；把页面转 90°，屏幕上没转；
加了水印，看不见那个水印 —— 要看到结果，只能"保存修改为…"写出一份新文件，
再由 `documentSavedAs` 在**另一个标签**里把它打开。

这是七样结构编辑共同的形状，也是编辑这一半**最大的一条功能缺口**。
我不认为现在就该做全量"所见即所得"（那要把编辑后的页树接回渲染路径，是 v2 的工程），
但至少有两条便宜得多的中间路可选：

- **(a) 让侧栏缩略图反映操作列表**。删掉的页在缩略图上划掉或移走、重排后顺序跟着变、
  旋转跟着转 —— 不碰渲染路径，只动 `ThumbnailPanel` 的模型。
  七样里有五样（删 / 转 / 重排 / 合并 / 拆分）能在这一层被看见。
- **(b) 保存之后，给"用新文件替换当前标签"一个选项**。现在是固定开新标签（注释里写了理由，
  那个理由对"检查删对了没有"成立），但对"我就是要编辑这份文件"的人，两个标签是负担。

这一条要你定走哪条，所以先不写成"必须改"。

## 二、新查出来的缺陷（这一轮的产出）

### 2.1 【严重】打开任何文档，立刻把**整本书**的缩略图渲一遍 —— 而侧栏默认是关着的

`documenttab.cpp:651`：

```cpp
outlinePanel->setOutline(backend->outline());
thumbnailPanel->start(sizes, backend.get());   // 无条件
```

`ThumbnailPanel::start()` 起一个 `QtConcurrent::run`，**从第 0 页到最后一页**挨个
`document->render(...)`，中间不看侧栏是否可见、不看用户在读第几页、没有任何优先级。
而 `sidebarWanted` 的初值是 `false`（`documenttab.h:399`）—— 侧栏默认不显示。

为什么这件事疼：Qt PDF 的每一次 FPDF 调用都走**同一把全局递归锁**
（`QPdfMutexLocker : std::unique_lock<QRecursiveMutex>`，`qpdfdocument_p.h`，
§ 这一条 review-01 时核过 Qt 私有头）。缩略图 worker 占着锁的每一刻，
用户正在等的那一页就在排队。

**量出来的数**（`xyzpdf_pdfprobe`，这台机器，2026-10-22）：

| 文件 | 缩略图尺寸渲一页（160 px 宽） | 整页渲一页（2500 px 宽） |
|---|---|---|
| `tests/fixtures/scan.pdf`（300 dpi 纯图） | **17 ms**（最差 27） | 30 ms |
| `tests/fixtures/huge.pdf`（合成文字） | **0 ms**（最差 2） | 3 ms |

关键在扫描件那一行：**把输出缩到 1/15，耗时只降到 57%** —— 因为成本在解码，不在采样。
推下去：一本 500 页的扫描书，打开的那一刻就排进 **约 8.5 秒**的 PDFium 工作量，
全程和用户正在看的那一页抢同一把锁，而这 8.5 秒是为一个默认不显示的侧栏干的。
文字文档上这条几乎不疼（600 页 ≈ 0.3 秒），**所以它正好只在最慢的那类文档上发作**。

这和他 9 月报的"非常卡"是同一族的第二层：review-02 修的是内存，这一条是锁。

改法（按便宜程度）：
1. `start()` 推迟到侧栏第一次可见（`applySidebarVisibility()` 里，或 `ThumbnailPanel::showEvent`）；
2. 只渲**视口里那几行**缩略图 + 预取一屏，滚动时续渲 —— 和 `PageView::requestVisiblePages()`
   同一套思路，`QListView` 的 `verticalScrollBar()` 给得出范围；
3. 渲染顺序从**当前页**向两边展开，而不是从第 0 页。

第 1 条一行能改完，先做它。

### 2.2 【中】缩略图没有上限，按页数线性增长，而且不计入任何预算

每张缩略图以 `QIcon` 存进 `QStandardItemModel`，**永不淘汰**。
`thumbWidth = 120` → 120×170 ARGB32 ≈ 81 KB/页。600 页 ≈ **49 MB**，
1000 页的书 ≈ 80 MB，全在 `RenderCache` 那个 256 MB 预算**之外**。

这正是 review-02 第 1 条的形状（"认真算过的预算约束不到真正占内存的那一份"），
只是换了一层：那次是 `PageView::images`，这次是缩略图模型。
修 2.1 的第 2 条（只渲可见的）顺带就把这条修了 —— 两条是一件事的两面。

### 2.3 【中】Ctrl+滚轮在精密触控板上什么都不做

`pageview.cpp:1518`：

```cpp
const int steps = event->angleDelta().y() / 120;
if (steps == 0) { event->accept(); return; }   // 余量被丢掉
```

鼠标滚轮一格是 120，所以鼠标上没问题。但 Windows 精密触控板（PTP）和高分辨率滚轮
送来的是小增量（典型 ±20…±40 一事件），`/120` 整除恒为 0，余量又被 `accept()` 吞掉 ——
**两指捏合/Ctrl+两指滚动永远不会缩放**，而且因为事件被 accept 了，也不会退化成滚动。

改法是标准那一套：留一个 `int wheelRemainder` 成员，`remainder += angleDelta().y()`，
`steps = remainder / 120`，`remainder %= 120`；换文档/换方向时清零。
`zoom_smoke` 里可以直接钉公式（它已经在测以光标为锚的那条），不必上屏幕。

**没验的一层**：这台机器上没有触控板，这条是读代码读出来的，不是在屏幕上按出来的。
改完要在一台笔记本上按一次，或者至少用合成的 `QWheelEvent(angleDelta=40)` 连发三次
断言缩放发生了一次。

### 2.4 【待验，不写成缺陷】前台打印 / 图片导出里 `processEvents()` 的重入面

`DocumentTab::print()` 与 `exportImages()` 都是**前台同步**跑的，每页回调里一句
`QApplication::processEvents()`（为了让进度框能画、取消键能按）。进度框是
`Qt::WindowModal`，所以窗口上的**输入**被挡住了。

没挡住的有两条，而两条都没人测过：

- `WM_CLOSE`（任务栏右键关闭 / Alt+F4）在 Qt 里不是输入事件，模态拦截不一定管它。
  若它穿过去 → `MainWindow::closeTab()` → `tab->deleteLater()`，
  而 `deleteLater` 的投递**正好会被这句 `processEvents()` 执行** ——
  于是 `DocumentTab` 在自己的 `print()` 还在栈上时被析构，`Print::run(*backend, …)` 的
  引用随即悬空。
- 单实例网关：第二次启动把文件转发进来，`applyForwardedCommandLine()` 也在这句里跑。
  这条看起来是安全的（它只开新标签），但同样没测过。

写成"待验"而不是"缺陷"，因为我没让它崩过。
验法很便宜：`mainwindow_smoke` 里起一次导出，在回调第 2 页时投递一个
`QEvent::Close` 给窗口，看进程还在不在。能红就修（最直接的修法是导出期间
`setEnabled(false)` + 一个"正在导出，不能关闭"的 `closeEvent` 拦截）。

## 三、对着 PLAN 少的功能

M0、M1、M3、M4 逐条对过，**除下面四条外全部落地**（标签拖出成窗口、会话恢复、
跳转列表、夜间反色、双页/书籍、演示、打印、图片导出、右键菜单、预览窗格、
缩略图处理器、外链点击前确认、双击选词、跨页选择 —— 都在，都有测试）。

### 3.1 文档属性对话框：方案里有，后端有，界面**一个字都没有**（M2）

PLAN M2 明写"文档属性对话框"。实际：
- `DocMetadata`（标题/作者/主题/关键词/生成器/创建者/两个日期/是否加密）**写好了**；
- `QtPdfBackend::metadata()` **实现了**，`document_smoke:208` **测了**;
- 全仓库 `grep '属性'` → **0 命中**；`DocMetadata` 的使用者只有测试。

也就是说这是整个 M0–M3 里唯一一条"做了一半、剩下的半条是纯 UI"的。
一个 `PropertiesDialog`（走 `WindowDialogs`，一张只读的键值表，加一行文件大小与路径）
加一条菜单项就完。**它还是"上架前用户第一个会去找"的那类框**。

### 3.2 搜索：缺"全词匹配"和"结果列表"（M2 两处原话）

现在有：增量搜索、区分大小写复选框、第 N / 共 M 个计数、上一个/下一个、
当前项与其余项两种深浅的高亮（`drawRanges` 112 / 150 两档）。

缺：
- **全词匹配**。`TextSearch::matchesInPage()` 只有 `caseSensitive` 一个开关。
  加一个 `wholeWord` 参数在这一层很便宜（它是纯函数，`textsearch_smoke` 直接能钉），
  **但 CJK 没有词边界**，所以这个选项对中文文档的语义要先想清楚再写
  （一般做法：只用 `QChar::isLetterOrNumber` 判两端，CJK 字符之间视为有边界 ——
  这个决定要写进注释，不然下一个人会以为它坏了）。
- **结果列表**。M2 原话是"结果列表"，现在只有一个计数。一本书里 200 个命中，
  用户只能一个个 Enter 过去。这条的工作量比上一条大（要文字上下文片段 + 页号 + 点击跳转），
  可以放在属性框之后。

### 3.3 区域截图到剪贴板：只长在"识别"框里（M3）

M3 原话是一条独立能力。现在的路径是：选"识别"工具 → 拖一个框 → OCR 框弹出来 →
框里有一个"复制图片"（`ocrdialog.cpp:50`）。

功能上够得着，但**名字不对**：想复制一张图的人不会去点"识别"，
而且每拖一个框都会白白跑一次 WinRT OCR。
便宜的修法：给"选择"工具的框选加一个右键菜单（复制图片 / 识别 / 翻译），
或者工具栏上单列一个"截图"。

### 3.4 没有"重新加载"，而且开着的文件别人删不掉 / 覆盖不了

- 全仓库没有 `QFileSystemWatcher`，也没有任何"重新加载/刷新"命令。
  对着一份 LaTeX/Word 反复重新生成的 PDF 读的人，每次都要关掉再开。
- §66 量过：PDFium 开文件不带 `FILE_SHARE_DELETE`，所以文件被锁住。
  那一片**只修了预览窗格那一支**（读 `%TEMP%` 里的副本），
  主窗口这一支照旧锁着 —— 也就是"XYZPDF 开着那份 PDF，Explorer 里删不掉、
  别的程序也覆盖不了"。§66 同时量掉了"换成我们自己的 QIODevice"这条路
  （`documenttab_smoke` 挂死 600 秒），所以要修只剩"像预览窗格那样读副本"这一条，
  代价是大文件要复制一份。

这两条是一件事的两头：有了 watcher 和重新加载，"锁"的疼法会变（文件被覆盖后能一键重读），
所以要做就一起想。**现在两条都没有，先记上。**

## 四、项目自己记着的欠账（按"外人第一眼能不能看见"排序）

这些都在 `docs/store-submission.md` 里有出处，我只是把它们按影响重排一遍，
因为那份文档是按时间长的，而"该先修哪个"看不出来。

1. **表单字段一个像素都不画**（§54 → §82 → §94）。量到底了：同一份 `/AP /N` 挂在
   `/Square` 上画满 6000 格、挂在 `/Widget` 上一格不画，六条路径（页面 / 缩略图条 /
   壳缩略图 / 预览窗格 / 导出 / 打印）**全是 widget=0**。
   **用户影响最直接的一句话是 §94 那句：打印一份填好的表单，字段是空的。**
   外部用户第一眼能看见的缺陷里，这条排第一 —— 而它目前挂在"等你定"（要不要自画 `/AP`）。
   我的看法：在决定自画之前，**至少先在打开带表单的文件时说一句**
   （"这份文档含表单字段，本版不显示其内容"），一句话比一张白纸强。
2. **侧栏点书签只跳页号，不跳页内位置**（§99 第 7 条）。目的地现在**已经写进文件**了
   （别的阅读器读得到），只有我们自己不跳。这条是"自己家的功能没接上自己家刚做好的数据"，
   修起来不碰文件格式。
3. **就地保存与文件锁**（§79）、**`/Brepro`**、**XFA**（§55）、**§47 那句读者可见的话** ——
   四条都明写"等你定"，不是忘了。
4. **§16 那"三处相同"欠 §84–§99 十六片**：构建树 / 包内 / 装上的三处字节比对，
   最后一次对上是 §83。这是发布前必须还的一词（重打包 + 重装），不是可选项。
